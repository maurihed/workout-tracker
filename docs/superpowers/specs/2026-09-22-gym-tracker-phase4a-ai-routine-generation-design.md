# Gym Tracker — Phase 4A AI Routine Generation — Design Spec

- **Date:** 2026-09-22
- **Status:** Proposed
- **Author:** Mauricio Hernandez (with opencode)
- **Parent spec:** `docs/superpowers/specs/2026-09-22-gym-tracker-design.md` (binding, §16)
- **Depends on:** Phases 1–3B (merged)
- **Sibling:** Phase 4B (personalization/refinement from history) — separate spec/plan

## 1. Objective

Let a user ask for a **personalized routine** generated by an LLM, validated against a strict
schema, resolved against the exercise catalog, previewed, and saved — with a deterministic
fallback so the feature never hard-fails, and a safety disclaimer.

### Success criteria

- A user submits goal/experience/equipment/days-per-week and gets a generated routine to preview.
- The model's output is validated (Zod) against a strict contract; invalid output triggers bounded
  retries and then the deterministic template fallback.
- Exercises are resolved to catalog entries; unmatched names become custom exercises.
- The user must confirm before the result becomes a saved routine; provenance is recorded.
- Generation runs as an async job (pg-boss) with status polling, timeout, bounded retries,
  per-user quota, and cancel.
- All copy is localized (EN/ES); the disclaimer is always shown.

### Non-goals (out of scope for 4A)

- Personalization from workout history/PRs (Phase 4B).
- Streaming token-by-token output.
- Fine-tuning; multi-turn chat refinement.
- Generating exercise media.
- Social/nutrition features.

## 2. Inference hosting (spike outcome)

- **Provider-agnostic:** the generator calls an **OpenAI-compatible `/v1/chat/completions`**
  endpoint with `response_format: { type: "json_schema", json_schema }` and structured outputs.
  Env: `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL`, `AI_TIMEOUT_MS`. Missing config ⇒ fallback.
- **Default deployment:** a **hosted** OpenAI-compatible endpoint (cheap, zero-ops, structured
  outputs). **Self-hosted Ollama** on a GPU host is supported via the same interface
  (`AI_BASE_URL=http://ollama:11434/v1`); CPU-only Ollama on the Coolify VPS is **not** viable
  (1–8 tok/s). A GPU VPS is only warranted for hard data-residency requirements.
- Ollama's native `format` (JSON schema, `temperature: 0`) is used when the base URL is detected
  as Ollama; capability is expressed through the provider adapter.

## 3. Data model

New `AiJob` (parent §8.2) + minimal routine provenance:

```prisma
enum AiJobStatus {
  queued
  running
  succeeded
  failed
  cancelled
}

model AiJob {
  id            String      @id @default(cuid())
  userId        String
  status        AiJobStatus @default(queued)
  input         Json
  result        Json?
  model         String?
  promptVersion String?
  error         String?
  attempts      Int         @default(0)
  createdAt     DateTime    @default(now())
  startedAt     DateTime?
  finishedAt    DateTime?

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, createdAt])
  @@index([status])
}
```

- Changes to `Routine`: add `aiJobId String?` (nullable link to the job that produced it) so
  provenance is queryable; `source` becomes `"ai"` for accepted generations.
- Back-relation: `User.aiJobs AiJob[]`.

## 4. Generation pipeline

`src/server/services/ai/`:

- **`prompt.ts`** — pure `buildPrompt(input, catalogSummary)` and `PROMPT_VERSION`. The prompt
  pins the JSON contract, forbids prose, and enumerates allowed catalog `sourceId`s.
- **`contract.ts`** — the strict Zod `generatedRoutineSchema`:
  ```
  { name: string, goal?, days: [ { weekday 0..6, label?, exercises: [
      { sourceId?: string, name?: string, sets 1..10, reps string, restSeconds 0..3600,
        targetWeightKg?, timerType none|interval|emom|amrap, workSeconds?, rounds? } ] } ] }
  ```
  plus `normalizeGeneratedRoutine` (trim, drop empty days, de-dupe) and validation error extraction.
- **`provider.ts`** — `AiProvider` interface (`generateJson(prompt, jsonSchema) → unknown`); an
  `OpenAiCompatibleProvider` (fetch, `response_format`, timeout) and an `OllamaProvider`
  (`/api/chat`, `format`). Selected from env; if unset, `generateJson` throws `AiUnavailableError`.
- **`resolve-exercises.ts`** — pure `resolveExercises(generated, catalogIndex)`: match by
  `sourceId`, else case-insensitive/trimmed name, else fuzzy (token overlap) → catalog id; unmatched
  → custom exercise (`customName` + placeholder image). Returns the routine payload plus a list of
  custom names.
- **`template-fallback.ts`** — deterministic routine from `/api/routine-templates` semantics by
  goal/experience/equipment/days; guaranteed valid, `source: "template"`, no model needed.
- **`ai.service.ts`** — `createJob(userId, input)`, `getJob(userId, id)`, `listJobs(userId)`,
  `cancelJob(userId, id)`, `runJob(jobId)` (the worker entry), `acceptJob(userId, jobId)` (creates
  the `Routine` with provenance, idempotent). Quota + rate limiting via the existing Postgres limiter.

**Job lifecycle:** `POST /api/ai/routines` validates input, enforces quota, creates an `AiJob`
(`queued`), and enqueues `ai-routine` on **pg-boss**. A worker (`pnpm worker:ai`, a long-running
process on Coolify) claims the job (`running`, `startedAt`), calls the provider with a timeout,
validates + normalizes + resolves exercises, and stores `result` (`succeeded`, `finishedAt`). Any
failure (unavailable/timeout/invalid after bounded retries) stores `error` and, unless the job was
cancelled, falls back to the deterministic template result with `source: "template"` so the user
still gets a routine. Bounded retries (≤3) with a repair prompt. `cancelJob` sets `cancelled` and
removes the pending queue entry.

## 5. API

Conventions unchanged: thin handler → service → repository; `{data}`/`{error}`; auth-scoped.

| Method & path | Purpose | Response |
|---|---|---|
| `POST /api/ai/routines` | create a generation job | `202 { data: AiJobDTO }` (queued); `429` over quota |
| `GET /api/ai/routines` | list the user's jobs | `{ data: AiJobDTO[] }` |
| `GET /api/ai/routines/[id]` | poll status | `{ data: AiJobDTO }` (`result` when succeeded) |
| `POST /api/ai/routines/[id]/cancel` | cancel | `{ data: AiJobDTO }` |
| `POST /api/ai/routines/[id]/accept` | save as a routine | `201 { data: { routineId } }` (idempotent) |

`AiJobDTO = { id, status, input, result: GeneratedRoutineDTO | null, model, promptVersion, error,
createdAt, startedAt, finishedAt }`. Input: `{ goal, experience, equipment[], daysPerWeek,
focus? }`, validated by `aiJobInputSchema`.

## 6. UI

- `/[locale]/(app)/routines/generate` (and a CTA on the routines page): a form (goal,
  experience, equipment multi-select, days/week) → create job → **poll** every ~2s with progress
  states → when succeeded, a **preview** screen rendering the generated routine (day/exercise cards,
  custom-exercise markers) with **Accept & save** / **Regenerate** / **Discard**.
- **Safety:** a persistent disclaimer (suggestions, not medical advice) and an explicit confirm to
  save; injury/health note.
- **Provenance:** the saved routine records `aiJobId`/`model`/`promptVersion`; the routine card marks
  AI-generated routines.
- Fallback (template) results are previewed identically and labeled as template-generated.
- Mobile-first, ≥44px, no hardcoded copy.

## 7. i18n

New `ai.*` namespace in both locales (parity): form labels (goal, experience, equipment,
daysPerWeek, focus), progress states (queued/running/succeeded/failed), preview actions
(accept/regenerate/discard), custom-exercise note, provenance label, and the safety disclaimer.

## 8. Testing

- **Unit:** `buildPrompt` (pins contract + catalog ids), `generatedRoutineSchema` (accepts valid,
  rejects malformed), `normalizeGeneratedRoutine`, `resolveExercises` (sourceId → name → fuzzy →
  custom), template fallback validity, provider adapter request shape (MSW) incl. timeout.
- **Integration (Postgres):** job create/enqueue/claim/run lifecycle with a **fake provider**;
  invalid-then-valid retry path; provider-unavailable → template fallback result; quota `429` and
  rate limiting; cancel; `accept` creates a `Routine` with provenance and is idempotent; ownership
  404.
- **Component (RTL):** the generate form validates input; polling progress states; preview renders
  days/exercises and custom markers; accept/regenerate/discard.
- **E2E (Playwright, mocked provider):** request → polling → preview → accept → the routine appears
  in the routines list with provenance.
- **Gates:** lint, typecheck, unit, integration, coverage, build, e2e.

## 9. Risks & mitigations

| # | Risk | Mitigation |
|---|---|---|
| 1 | Invalid/partial model JSON | Zod validation + bounded repair retries + deterministic template fallback |
| 2 | Model unavailable / timeout | Provider abstraction + timeout + fallback result |
| 3 | Long latency | Async job + polling; the request returns immediately |
| 4 | Prompt injection / bad output | Strict JSON schema + prose forbidden + client/server validation |
| 5 | Abuse / cost | Per-user quota + Postgres rate limiter; hosted-by-default keeps cost low |
| 6 | Unmatched exercises | Fuzzy match + custom-exercise fallback with placeholder |
| 7 | Provenance missing | `AiJob` stores model/prompt version/input; `Routine.aiJobId` links it |
| 8 | Health claims | Persistent disclaimer + explicit confirm; no medical advice |
| 9 | pg-boss worker not running | Health check + job stays `queued`; UI surfaces "queued" and a retry/cancel |

## 10. Acceptance criteria

- A user requests a routine and receives a validated, personalized result to preview.
- Invalid output falls back to a valid deterministic template routine (feature never hard-fails).
- Unmatched exercises become custom exercises.
- The user confirms before it is saved; provenance is recorded and the routine is marked AI-generated.
- The job lifecycle supports queuing, polling, timeout, retries, quota, cancel, and idle-worker visibility.
- A persistent safety disclaimer is shown.
- All gates green; EN/ES parity; ≥44px; no hardcoded copy.
